# Apps plan (October 2)

What the phone still needs to be a daily phone: core apps, a touch browser,
Android apps through Waydroid, and Bluetooth LE for phone-as-key
accessories. The order at the end is the one the user chose.

## How apps are built here

Apps live in `overlay/mobile/apps/<id>/`: a `manifest.json` (name, icon,
permissions) and a Quickshell `shell.qml`, started with `quickshell -p`. They
share the kit (`OmarchyMobile`: AppWindow, PageHeader, SettingsRow,
PinEntry, MobileTheme), the shell's back gesture (AppBack), the theme, and
the grant prompt for permissions. Helpers with real work (modem, database,
network) are Python scripts in `overlay/mobile/` installed as
`omarchy-mobile-<name>`. Phone, Messages, Contacts, Files and Camera are
built this way and run today.

Two limits shape the rest of this plan:
- Quickshell cannot host QtWebEngine: WebEngine must be initialized before
  the application object exists, and Quickshell 0.3.1 has no way to do that.
  A browser needs its own small host program, and the kit's components that
  import Quickshell (Process, FileView) are not available to it.
- The session still runs as root. Chromium-based engines refuse to sandbox
  as root, and Waydroid expects a user session. The planned standard user
  session (see the roadmap) comes before a browser or Waydroid ships.

## Core apps

Built as Quickshell apps, smallest first. Each lists the OS piece it needs
beyond what exists.

| App | Scope | Needs |
|---|---|---|
| Calculator | Basic and scientific (landscape), history, copy result. **Built October 2** (`apps/calculator`: calc.js's parser, no eval) | Nothing new |
| Clock | Alarms, timer, stopwatch, world clocks | Alarms that wake the phone from deep sleep (below) |
| Notes | Plain/Markdown notes in `~/Notes`, search, share. **Built October 2** (`apps/notes`, `notes.py`; copy rather than share) | Nothing new |
| Photos | The camera roll and other image folders, full-screen viewer, share, delete | Thumbnail cache; the Camera app's gallery becomes a link to it |
| Music | Local library, MPRIS, controls in the shade and on the lock screen | Lock-screen media controls; audio focus already follows the role rules |
| Recorder | Voice memos | Microphone (works) |
| Calendar | Agenda/month, local calendars, CalDAV sync later | The shade's month view links to it |
| Maps | Later: OSM tiles, search, location | GNSS fix (the BCM4776 reaches chip ID; NMEA is still open) |

**Alarms are the one hard part of Clock.** An alarm has to ring with the
phone in deep sleep, the screen off, and Do Not Disturb on. The pieces are
mostly there:
- The sleep adapter already wakes at set times: the minute tick under the
  always-on display and the background check. An alarm service gives it the
  next alarm time; it wakes at the earlier of that and the next check.
- The audio policy already has an Alarm role, which is heard through Silent
  and ducks other sound.
- The alarm screen goes above the lock, like the incoming-call screen
  (`above_lock = 2`), with snooze and dismiss. Vibration uses the haptics
  control.

Verify with an alarm a few minutes out, unplugged, after the phone has been
dark long enough to reach SYS_SLEEP.

## Calendar and contact sync (later)

Calendars are iCalendar files and contacts are vCards, each in a vdir
folder (`~/.local/share/omarchy-mobile/calendars/<calendar>/`,
`.../contacts/`). That is the layout vdirsyncer syncs, so accounts can be
linked later without changing the apps:
- **CalDAV/CardDAV through vdirsyncer:** iCloud, Fastmail, Nextcloud, and
  Google (its calendar storage logs in with OAuth).
- **Microsoft 365:** has no CalDAV, and Microsoft is retiring EWS (which
  gateways such as DavMail use) in Exchange Online. It needs a small
  connector on the Graph API that writes the same vdir files.
- **Settings → Accounts:** add an account, choose which calendars and
  address books sync, and sync at the background check (no wakes of its
  own).

## Browser

**Recommendation: our own browser on QtWebEngine.** It is the same Chromium
engine Omarchy uses on the desktop, with a phone UI written for this shell:
- A bottom address bar; the shell's left-edge back gesture is page Back.
- Swipe on the bar to switch tabs. A tab overview of cards, like the app
  switcher.
- Pull to refresh, pinch zoom, a mobile user agent, and full-screen video.
- Colors from the current Omarchy theme, as the shell takes them. A web
  page's own theme color can tint the bar.
- Downloads go to `~/Downloads`. Camera, microphone and location prompts
  match the shell's.
- Web apps (`overlay/mobile/webapps`, now Chromium app mode) open in the
  same engine without the browser chrome.
- A built-in content blocker (EasyList through WebEngine's request
  interceptor), because WebEngine has no extensions.

The host is a small C++ program: it initializes WebEngine, registers the
interceptor and a theme reader, and loads a QML UI from
`overlay/mobile/apps/browser/`. `qt6-webengine` 6.11.2 is in Arch ARM's
`extra`.

**What it gives up:**
- Chrome extensions.
- Widevine DRM: no Netflix-class streaming without extra work.
- Engine updates follow Qt's WebEngine releases, a few weeks behind
  Chromium security fixes.

**Alternatives considered:**
- **Desktop Chromium:** current engine and extensions. Its UI is
  mouse-first, and themes reach only the frame color through policy.
- **Firefox with postmarketOS's mobile-config-firefox:** a mature phone
  layout, uBlock Origin, and themable through a generated `userChrome.css`.
  But the gestures are Firefox's, not the shell's. It is the fallback if our
  own browser stalls, and a usable stopgap meanwhile.
- **GNOME Web:** adaptive, but libadwaita-themed. It would never match an
  Omarchy theme.

**Milestones:**
1. Host and one tab: address bar, back gesture, theme, the user session
   (no root).
2. Tabs, the overview, pull to refresh, downloads, permission prompts.
3. Content blocker, web apps in the engine, full-screen video, and a text
   field that brings up the keyboard reliably.
4. Bookmarks and history search, and sync with the desktop later (see
   "Phone/desktop integration" in the roadmap).

## Android apps: Waydroid

Waydroid runs a LineageOS-based Android in a container. In multi-window mode
each Android app is its own Wayland window with a desktop entry, so Android
apps show up in the shell's drawer and switcher like any other app.

**This kernel already has most of what it needs:**
- binderfs, with `binder`, `hwbinder` and `vndbinder`.
- User, PID, network, IPC and UTS namespaces.
- cgroups, including the freezer.
- memfd and seccomp.

`waydroid` 1.6.3, `lxc` 7.0 and `python-gbinder` are all in Arch ARM's
`extra`, and the root has 223 GB free.

**Missing:**
- **Netfilter in the kernel (checked October 2).** Only the conntrack core,
  `ip_tables`/`ip6_tables`, a few `xt` matches, `bridge` and `veth` are
  built, as modules.
  - NAT, nftables and the `filter`, `mangle` and `raw` tables are not
    configured at all.
  - Waydroid's network script masquerades the container through
    nftables or iptables NAT. Android's `netd` sets up its own `filter`,
    `mangle` and `raw` rules inside the container.
  - These can't be added as modules to the running kernel: `CONFIG_NF_TABLES`
    adds a member to `struct net`, which built-in code shares. They belong
    in the next image's configuration, as Arch's kernels have them (mostly
    `=m`). The same change means every out-of-tree module that uses
    networking structures has to be rebuilt with that image: the modem
    bundle's `cpif`, brcmfmac, and the Bluetooth modules. The options:
    - `NF_NAT`, `NF_TABLES` with `inet`, `nat`, `masq`, `ct` and `fib`;
    - `IP_NF_FILTER`/`MANGLE`/`RAW`/`NAT`, `IP_NF_TARGET_MASQUERADE`/`REJECT`
      and the IPv6 equivalents;
    - `NETFILTER_NETLINK*`;
    - the `xt` matches and targets in Android's base config (`bpf`,
      `owner`, `quota2`, `socket`, `connmark`, `mark`, `comment`, `limit`,
      `string`, `u32`, `IDLETIMER`, `NFLOG`, `TCPMSS`, `CT`).
  - **Shipping modules:** the phone has no `/lib/modules` tree; modules load
    by path from the initramfs or `/usr/local/lib/omarchy-mobile`. With a
    `/lib/modules/<release>` tree on the root (and `depmod`), `modprobe` and
    the kernel's own `request_module` find them. The tree is too big for
    the initramfs.
  - **Alternative for the container's network:** `pasta` (passt) gives a
    network namespace a tap device and user-space NAT over TUN, which this
    kernel has (`=y`). LXC would start the container with an empty network
    and attach pasta to it, with no kernel NAT or bridge. `netd`'s own rules
    would still need the iptables tables.
- **GPU in the container.** Android needs its own Mesa with the panthor
  driver (Mali-G710 is CSF hardware: Mesa 24.1 or newer). Check the Mesa in
  the current Waydroid arm64 image first. Without panthor, Android renders in
  software, which is fine for simple apps and too slow for games or maps.
- **A user session.** Waydroid's session runs as a user.

**Power:** a running Android container costs battery even when idle. It
should follow the "off unless needed" rule:
- Start it on the first launch of an Android app.
- Freeze it with the cgroup freezer once no Android window has been open
  for a while.
- Stop it later still.
- Android's own push notifications (FCM) only arrive while it runs. Apps
  that need push stay a known gap, not a reason to keep Android running.

**Milestones:**
1. Kernel modules; install `waydroid`/`lxc`; initialize with the arm64
   image; one app on screen in multi-window mode.
2. GPU acceleration, or a decision to run software-rendered.
3. Shell integration: Android apps in the drawer with icons, Android
   notifications forwarded to the shade, the shell's back gesture sent as
   Android Back, and the keyboard.
4. The freeze and stop policy; F-Droid as the app store.

## Bluetooth LE for phone-as-key accessories

This is OS work only; the apps that use it live in their own repositories.
Bluetooth works today: firmware, BlueZ, and an LE scan that saw 24 devices.
In order:
1. **Userspace checks:** LE Secure Connections pairing, a GATT server and
   client over BlueZ D-Bus, advertising, and connection RSSI. These need a
   second LE device to test against.
2. **Chip low-power mode:** device-wake and host-wake through pinctrl, so
   the chip sleeps between events instead of being held awake as it is now.
3. **Through deep sleep:**
   - SYS_SLEEP cuts the chip's power today, because BT_REG_ON is a PERIC0
     pad that turns into an input in sleep. Hold it, and the chip's supply,
     through sleep.
   - Unmask the host-wake interrupt in `pixel-sleep`, like Wi-Fi's wake line
     and the new touch wake.
   - Stop unloading `hci_uart` before sleep when a key is in use.
4. **Filters in the controller:** BlueZ advertisement monitors and Broadcom's
   advertising filters, so only a known device wakes the phone, then
   reconnect and RSSI on wake.
5. **Measure:** the cost of keeping LE alive in sleep, against the current
   unplugged average.

## Order (decided October 2)

The user chose our own QtWebEngine browser, the move to a standard user
session, and this order:
1. Clock: alarms, timer, stopwatch, world clocks; alarms through the sleep
   adapter.
2. Calendar.
3. The standard user session, which the browser and Waydroid need.
4. Browser milestones 1 and 2, then 3 and 4.
5. BLE steps 1 to 3, interleaved with the power work.
6. Then Calculator, Notes, Photos, Music, Recorder; Waydroid; Maps after GNSS.
