# Calling, texting and the phone apps — September 27, 2026

Follows [the SIM and cellular bring-up](cellular-sim-20260926.md). Texting now
works in both directions, and **VoLTE calls work with audio both ways**:
earpiece, microphone, speaker, mute, and the proximity sensor blanking the
screen against a face. Omarchy-themed Phone, Messages and Contacts apps replace
the idea of GNOME Calls and Chatty.

## Results

- **SMS both ways.** A text to the user's number was delivered, and the reply
  arrived over IMS (WMS transfer-route MT with the "SMS on IMS" TLV) and was
  acknowledged by ModemManager.
- **VoLTE call, no audio (first night).** The user dialled out from the new
  Phone app. The modem reported `type voice-ip, mode lte`; the call was
  answered and ended after 20 s. That 20 s turned out to matter (below).
- **VoLTE call with audio (September 27, midday).** An incoming call rang
  (vibrate), answered from the shell's screen, and carried audio both ways
  past 30 s; speaker and mute worked, and the proximity sensor blanked the
  screen at the ear.

## Why not GNOME Calls and Chatty

Both are in the Arch ARM repositories, but the phone's package database is
stale (two dependencies 404) and they would pull in about 490 MB of GNOME
stack (evolution-data-server, webkit2gtk). They also cannot follow the Omarchy
theme. The shell already has the pieces (Quickshell apps with Python helpers,
volume groups, vibration, display wake), so the apps are native.

## The apps

All three live in `overlay/mobile/apps/` and draw every colour from
`MobileTheme`, which follows the current Omarchy theme live. Answer and end
use the theme's own `green` and `red` (`color2` and `color1` in older
palettes). A shared `Avatar` shows a contact photo or initials, round or
square as the theme's corners are.

| App | Helper | Grants | Storage |
|---|---|---|---|
| Phone | `phone.py` → `omarchy-mobile-phone` | `phone`, `contacts` | recent calls `~/.local/state/omarchy-mobile/phone/history.json` |
| Messages | `messages.py` → `omarchy-mobile-messages` | `messages`, `contacts` | SQLite `~/.local/share/omarchy-mobile/messages/messages.db` |
| Contacts | `contacts.py` → `omarchy-mobile-contacts` | `contacts`, `files.home` | one vCard 3.0 file per contact, `~/.local/share/omarchy-mobile/contacts/` |

- **Phone:** keypad (long-press 0 for +, press Call on an empty keypad to
  recall the last number), recents with contact names and missed calls, a
  contacts tab, and the call screen (mute, keypad for touch tones, speaker,
  end; answer and decline while ringing).
- **Incoming calls** belong to the shell (`IncomingCall.qml`): a full-screen
  answer/decline layer over everything, the display woken (`omarchy-mobile-display wake`),
  a generated ringtone through the ring volume group and vibration, all
  following the alert slider and Do Not Disturb. A green chip in the status
  bar returns to a call in progress. Missed calls become notifications.
- **Messages:** conversations with unread counts and search, bubbles with
  day separators and delivery state (Sending, Sent, Delivered, Not sent with
  retry), a composer that counts SMS parts, new messages by contact or number,
  copy and delete. Received texts are copied out of the modem, stored,
  notified (with an Open button) and counted in the status bar, even when the
  app is closed: the shell runs `omarchy-mobile-messages watch`. Long texts go
  as several parts. MMS is not supported; a picture message shows a note.
- **Contacts:** favourites and an A–Z list with search, a contact page (call,
  text, favourite, every number, email, address, birthday, website, notes),
  an editor, photos from Camera, Pictures or Downloads cropped square
  (drag and pinch), import of vCard 2.1/3.0/4.0 and Google or Outlook CSV
  from Downloads/Documents, and export to `.vcf`. The files are plain vCards,
  so a later CardDAV sync (vdirsyncer) can use the same folder.

Plumbing shared by all three:

- `omarchy-mobile-app launch APP [ARG]` passes an argument
  (`tel:`, `sms:`, `thread:`, `uid:`, `new:`) as `OMARCHY_MOBILE_APP_ARG`, so
  the apps open each other on the right number, conversation or contact.
- Each `watch` command follows ModemManager through `gdbus monitor`. One
  watcher holds a lock and is the recorder (recent calls, copying texts,
  delivery reports, call audio start and stop); others only report.
- Texts are sent through `busctl`, so message text is never shell-quoted.
- Tests: `tests/test_phone.py`, `tests/test_messages.py`,
  `tests/test_contacts.py`.

## Call audio

A VoLTE or CS call's audio never passes through Linux: the modem hands voice
packets to the ADSP, whose voice services (MVM, CVS, CVP) run the vocoder and
connect it to two AFE ports. The AP only creates those sessions. Upstream
Linux has no driver for them; the msm8916-mainline and sdm845-mainline trees
do. The sdm845 version (commit `85f1df2`, branch `sdm845/7.1-dev`) is vendored
in `kernel/audio/q6voice/` with four patches: a 6.17 backport (API renames, no
internal MI2S ports), a `cvd_version` override plus start/stop logging, the
CVD version query with real port formats (0003), and the voice start moved
after the back ends (0004).
It uses the multimode session `11C05000` (VoiceMMode1), as the OnePlus 6 does.

- `scripts/build_voice_modules.sh` builds the six modules against the same
  tree and symbols as the running audio modules, and two overlay modules:
  `guacamole_voice_services` (MVM/CVS/CVP APR services, applied before the
  ADSP starts, since APR lists services only then) and `guacamole_voice_link`
  (the VoiceMMode1 front end on the card).
- `phone-audio-test.sh` and `phone-audio-modules.py` load them when
  `/root/audio-bringup/voice-enabled` exists; removing that file and rebooting
  returns to the previous audio stack.
- Routing: `QUAT_MI2S_RX Voice Mixer VoiceMMode1` (the amps) and
  `VoiceMMode1 Capture Mixer SLIMBUS_0_TX` (the handset microphone path that
  audio start already sets). `adapter/call-audio.sh` (installed as
  `~/.config/omarchy-mobile/call-audio`) does this per call, lets PipeWire
  release the device, and runs `call-audio-hold`, which holds both directions
  of the VoiceMMode1 PCM open (capture started) without moving data.
- Earpiece: the upper TFA9874 in its stock receiver profile. The lower amp
  would otherwise play the call too, so `tfa9874.c` gained a
  `Loudspeaker Switch` that keeps it off while its stream runs and switches
  live: Speaker in a call turns it on.

### Getting the uplink to work

The downlink worked at the first call; the microphone did not, and every call
ended after about 21 s. ModemManager's debug log gave the end reason: QMI
`REL_NORMAL` (0x19) with the SIP reason text `rtcp timeout`. The network
released the call because no RTP/RTCP came from the phone; the modem starts
its RTP transmit side only once the ADSP's encoder delivers uplink frames. So
both symptoms were one: no uplink frames. What it took, in order found:

1. **Answer did nothing** at first: `IncomingCall.qml` marked the call as
   being answered (hiding the screen, clearing `incoming`) and then read
   `incoming.id`, which threw. The id is now taken first.
2. **Start capture.** The PCM has no buffer, so the holder only prepares it;
   preparing starts the AFE ports and the amp, but WCD934x enables its SLIMbus
   TX channel only on a capture trigger. The holder now starts capture
   (`state: RUNNING`; the codec reports the TX port underflow at stop).
3. **CVD version.** The ADSP reports **CVD 2.4**. Patch 0003 queries it
   (`VSS_IVERSION_CMD_GET`), uses the v3 vocproc with channel info, the ports'
   real media format (48 kHz, 2 ch, 24 bit, as the machine driver's back-end
   fixup runs them; `q6cvp` module parameters) and topology commit.
4. **Start after the back ends** (patch 0004): the voice session starts in
   the front end's prepare, after DPCM has started the AFE ports, as the
   downstream driver orders it, instead of at open.
5. **The fix: TX topology NONE.** The default TX vocproc topology is
   single-mic ECNS (`0x10F71`), which needs calibration this phone never
   receives; without it the uplink is silent. `VoiceMMode1 TX Topology` =
   `0x10F70` (NONE) passes the microphone straight to the encoder; the
   adapter sets it at each call start. Audio both ways, no more drop.

Checks that ruled things out along the way: with the voice session running,
DAPM showed the whole microphone path powered (MIC BIAS1 → AMIC4 → ADC4 →
DEC0 → AIF1 CAP → SLIMBUS_0_TX → VoiceMMode1 capture), and MultiMedia2 on
the shared SLIMbus TX back end recorded real room noise, so samples did reach
the ADSP. Steps 2–4 are still right to keep (they match the downstream
driver); whether each is needed on its own was not isolated.

Adapter details: `call-audio` releases PipeWire's devices, sets the receiver
profile, turns the loudspeaker off (`Loudspeaker Switch`), routes both voice
mixers, sets the topology and starts `call-audio-hold` (which must not
inherit the adapter's lock, or `stop` would wait forever). Mute sets
`DEC0 Volume` 0; Speaker switches the lower amp on live.

### Proximity

During a call on the earpiece (not on speaker), the shell follows
`monitor-sensor --proximity` (the STK2232 through iio-sensor-proxy) and
covers the screen with a black layer that swallows every touch while it reads
near: on the AMOLED panel this is the screen off, and a cheek can no longer
end the call. The sensor is claimed only during such calls.

### SLIMbus enumeration race

One boot came up with no sound card: `SLIM Capture 1: codec dai not found`,
and a `__queue_work` warning from `qcom_slim_ngd_ssr_pdr_notify`. The SLIMbus
NGD driver registers for the audio PD's up notification before its child
device initializes the work that notification schedules; when the ADSP's PD
is already up the notification can win, the work is lost and the codec never
enumerates (2 of the recent boots). Reloading the module does not recover
(its remove leaks the child device, `-EEXIST`). `kernel/audio/slim-ngd-pd-up-race.patch`
initializes the work in the controller's probe, before the PDR lookup, and
lets it wait 5 s for QMI; `build_audio_modules.sh` applies it.

### First use of Messages

Sending and receiving worked. Two fixes after the user's first use:

- **The compose box ignored taps** (the user saw it start working only after
  20-30 s). Its tap handler sat inside the Flickable, so it covered only the
  content item (one text line), where the read-only TextEdit took the press
  itself. A MouseArea over the whole box now starts typing; while typing, a
  tap places the cursor and brings back a put-away keyboard. Reproduced and
  verified on the phone with the new touch tool: a tap 0.4 s after opening a
  new thread starts typing and shows the keyboard.
- **White text fields.** `TouchTextField` had no background of its own, so
  Qt's white field showed in Messages, Contacts, Files and Phone. It now
  defaults to the theme (surface, muted border, accent while editing, theme
  text, placeholder and selection colours and font); Settings' own styling
  still overrides.

`scripts/phone-touch.py` (with `out/input/uinput.ko`, uinput built for #194)
taps, holds, swipes and types through a virtual touchscreen, so UI flows can
be reproduced and checked with screenshots (`grim`) without a finger.

## Incident: the reboot helper froze the phone

`phone-crash-reboot.sh` was written for use after a modem crash. It stops
every Arch process, then remounts read-only with SysRq. Used on a healthy
phone, it also stopped `rmtfs` under a running modem, and the phone froze
(USB stopped answering at 01:30:49; no reboot). The user force-restarted it.
The helper now leaves `rmtfs`, `pd-mapper`, `tqftpserv` and `qrtr-ns`
running; SysRq-u does not need them gone. A modem crash freezing the whole
phone with IPA loaded is a separate robustness problem to confirm.

After the forced restart (USB disconnect at 01:35:41) the phone did not
reappear on USB, in fastboot or on Wi-Fi by 03:14: most likely powered off or
on a charge screen, waiting for a Power press.

## USB after a hard reset, and a Wi-Fi way in

After every forced reset (Power + Volume Up) the laptop never saw the phone
on USB, while warm reboots were fine; a replug did not help. The phone's own
boot diagnostics (`/root/bringup-logs/<boot>/`) show identical USB logs for
failed and good boots up to `gadget_pullup is_on=1`: the gadget binds and
connects, but the UDC stays `not attached`. The phone never sees the host;
the suspect is PM8150B's charger detection holding the data lines after a
full PMIC reset (our charger driver loads at ~142 s). Not yet confirmed.

So the phone is now reachable without USB:

- `sshd_config.usb` (started by the initramfs every boot) listens on all
  addresses, key-only, `AllowUsers` limited to private networks
  (10/8, 172.16/12, 192.168/16). `scripts/phone-ssh.sh` falls back to the
  Wi-Fi address in `out/network-test/wifi-host` when USB does not answer.
- The initramfs recovery shell on port 23 has no authentication and listened
  on Wi-Fi too. `adapter/network/remote-access.sh` (installed as
  `/usr/local/sbin/guacamole-remote-access`, run from session-prepare) moves
  it to the USB address at every boot; the reboot helpers still use it.
- The same step records the UDC state, dwc3 debugfs state and power-supply
  state at 90 s when USB is not configured, tries one soft reconnect and
  records the result, so the next failure has evidence.
- The phone's Wi-Fi has a static address (the user should reserve it in the
  router). Settings → Wi-Fi has an **IP address** section: Automatic (DHCP)
  on or off, with address, gateway and DNS fields, "Use current" and "Apply"
  (`omarchy-mobile-wifi ipv4`).

## Incident: a freeze emptied files written just before it

The 01:30 freeze left every file written in the minute before it empty
(ext4 delayed allocation): both audio scripts, all voice modules and even
the `.before-voice` backups. The audio start then refused to run on every
boot (checksum mismatch), so speakers and microphone were down too. All were
restored from the repository, and every deploy now ends with `sync`.
