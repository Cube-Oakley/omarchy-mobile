# Touch on the SPI0 controller with its interrupt — September 28, 2026

The S3908 touch controller now runs over the SoC's SPI0 controller with its
attention interrupt. Before this, the driver bit-banged the SPI pins and polled
the attention line. The driver is still `mainline/pixel-touch-input.c`; the
boot script loads it with `hwspi=1 irq=1` and falls back to GPIO polling if
that fails. Image V in `boot_a` carries it. Measured while the user dragged:

| | GPIO, polled | SPI0 + interrupt |
|---|---|---|
| Median interval between touch frames | 10.7 ms (heat map on), 3.8 ms (off) | 4.2 ms |
| Transfer cost | 23–70 µs per byte of busy CPU | 0.8 µs per byte, hardware-shifted |
| Worker CPU | several ms per frame | about 0.12 ms per frame, none when idle |
| Wakeups while idle | a poll every 1–8 ms | none (one interrupt per frame) |

In 1,062 frames there were 1,062 interrupts, with no SPI stalls and no
recoveries.

## SPI0

The stock DT `spi@10D10000` is `samsung,exynos-spi` with a 64-entry FIFO,
PERIC1 USI0 (`sysreg_peric1` 0x10c21000, USI offset 0), GIC SPI 690, a GPIO
chip select, mode 0 and a 10 MHz maximum. The bootloader leaves USI0
unconfigured, so the driver sets up:

- **Clock:** CMU_TOP's `MUX_CLKCMU_PERIC1_IP` selects `PLL_SHARED2_DIV2`.
  PLL_SHARED2 is 24.576 MHz × 130 / 4 = 798.72 MHz, and `DIV_PLL_SHARED2_DIV2`
  halves it. With no further division, USI0 receives 399.36 MHz; the
  controller divides by 4. The driver sets `DIV_CLK_PERIC1_USI0_USI` (CMU_PERIC1
  0x1808) to 10, for 9.98 MHz on the bus, and waits for its busy bit. The gates
  are left in automatic mode: the Q-channel is disabled with its clock request
  held.
- **USI:** SW_CONF is set to SPI (bit 1), then USI_CON leaves reset and
  USI_OPTION sets CLKREQ_ON and clears CLKSTOP_ON (SPI base + 0xc4/0xc8, as
  mainline `exynos-usi`).
- **Controller:** mainline `spi-s3c64xx` layout, GS101 port with 32-bit I/O
  only. Byte channel and bus width, polled FIFO, no DMA. Transfers go through
  the FIFOs in rounds of up to 64 bytes. The controller only clocks while its
  own chip select is active, so CS_REG is written 0 during a transfer even
  though the pad is a GPIO. The first attempt without that shifted nothing.
- **Pins:** gpp20-0/1/2 take function 3, as the stock `ts_spi_*_active`
  groups do. gpp20-3 stays the GPIO chip select.

Unloading, or handing the bus to AOC, puts the controller into reset and
restores the USI, the divider and the pins.

## Attention interrupt

gpa7-0 is a FAR_ALIVE wake-up EINT. That controller uses the exynos7 layout,
per its DT `wakeup-interrupt-controller`: ECON 0x700, EMASK 0x900, EPEND 0xa00.
The vendor `pinctrl-gs201.c` gives gpa7 EINT offset 4 at bank offset 0x20.
Its interrupt is GIC SPI 52, mapped from the DT `gpa7` node.
- **Setup:** the driver checks the inspected handoff (input, level low,
  masked), then sets pin 0 to the EINT function, clears its pending bit,
  requests the IRQ disabled, and unmasks pin 0 only.
- **Handler:** it disables the IRQ and wakes the worker.
- **Worker:** it reads packets while the line is low. When the line is high it
  clears the pending bit, re-enables the IRQ and sleeps; the level trigger
  fires at once if data arrived in between. A 200 ms timeout only lets the
  worker notice unload.
- **Level reading:** the pin's data register still reads the level with the
  pin in EINT mode.

## Still temporary

This is a register-level driver, not a Linux SPI controller plus a TouchComm
client: there is no clock framework or pinctrl support for GS201 PERIC1. The
recovery path, heat map disable and report parsing are unchanged from image T.
