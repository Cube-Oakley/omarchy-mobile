# September 30: capacity correction and deeper-idle bring-up

The installed battery-model image reports 5,002 mAh from the matched stock
Lishen profile, replacing the uninitialized 3,000 mAh gauge default. The
installed image retains the tested modem, USB switch recovery and key-only
Wi-Fi SSH. This capacity correction is not a standby-power measurement.

The later system-idle work remains opt-in. It is not enabled by the persistent
boot helper. The installed diagnostic image includes these default-disabled
options, the battery correction and persistent console logging; ordinary boot
uses the established sleep policy. The prior battery-model image is retained
as a recovery artifact.

## Validated prerequisites

- UFS Hibern8 system suspend enters and resumes with zero CDR timeouts; a
  synced 16 MiB test file remains intact. The feature defaults off.
- Read-only CPU/PCIe/ACPM checks showed the modem host powers down but the
  Wi-Fi host previously retained L1. Normally unloading Wi-Fi exposed idle
  opportunities with drained firmware queues.
- The CPU module now wraps both regular and frozen-tick idle callbacks.
  Frozen-tick idle uses an unbounded local timer deadline. Measurements use
  the architectural counter because monotonic time freezes during s2idle.
- A bounded, optional CPU 0 retry makes a little CPU enter last. Without it,
  CPU 7 entered last in a recorded trial, leaving no eligible little CPU to
  request the system mode. All physical-core and device guards remain.
- Optional Wi-Fi host PM reaches L2, powers down and isolates its PHY, then
  retrains and restores L1 substates before the network stack resumes. It
  preserves endpoint firmware power. The shared IRQ is synchronized before
  isolation, and isolation is released before any resume register access.

## Hardware evidence

A coordinated SICD hint covered 9.147 seconds of a 9.148-second RTC sleep,
with no cancellation or errors. Two later intervals covered 9.308 and 9.325
seconds. These alone did not establish a power saving: partial-rail totals
were 861.4/866.2 mW against controls of 863.1/863.2 mW.

A read-only ACPM named-buffer diagnostic then confirmed that an 8.369-second
combined Wi-Fi/UFS/SICD trial advanced the firmware's SoC-down and SICD
SoC-down counters from 0 to 1, with no early wakeup. The memory-interface
counter stayed 0 and its `mif_always_on` flag stayed 1. This is the remaining
firmware-policy lead; no policy flag was changed for that measurement.

Wi-Fi host PM passed an 8.604-second RTC cycle, and an 8.888-second combined
UFS/SICD cycle. Wi-Fi HTTPS and modem verification passed afterward. All
trials resumed in the same boot. The wake-enabled endpoint was first refused
cleanly; tests then temporarily disabled Wi-Fi wake and restored it afterward.
These tests do not establish wake-on-Wi-Fi, camera support, speakerphone, or
unplugged battery life.

## Defaults and recovery

`permit_sicd` and `sicd_defer` default false; `sicd_budget` defaults zero.
`system_link_off`, UFS `system_hibern8`, and watchdog `keep_running` also
default false. The extra system-mode mappings are only created when permitted.
The watchdog diagnostic reloads an already armed watchdog during short sleep;
it must be disabled for normal long sleeps. Reset recovery depends on its
clock continuing to run.

All trial scripts restore these runtime flags. No modem identity, SIM data,
firmware binary or private diagnostic output is tracked. The phone-side
modem manager owns radio control and the existing watchdog feeder throughout.
See the [CPU idle](../kernel/cpupm/README.md),
[Wi-Fi host](../kernel/pcie/README.md), and
[firmware diagnostics](../kernel/suspend/README.md) notes for implementation.

## Memory-sleep trial: not suitable for use

A subsequent RAM-only experiment followed the stock FLEXPMU debug control:
clear `MIF_ALWAYS_ON` only after all SICD guards pass, save its original value,
and restore it on wake or cancellation. The trial was limited to one entry
with a ten-second RTC alarm and an already armed watchdog left running.

The phone did not return through the trial cleanup. It reset and reconnected
roughly a minute later in the installed battery-model image. This timing is
consistent with the watchdog fallback, but no boot-reason field or persistent
crash record was available to confirm the reset cause or exact failure stage.
The pre-trial record was synced; no post-sleep counters were saved. Modem
verification, Wi-Fi access, the synced storage checksum and 5,002 mAh capacity
reporting all passed after recovery.

The MIF write API and its CPU-module option were removed from build sources.
The experimental patch and result remain private research artifacts. Only the
tested read-only firmware-counter implementation is retained. Do not infer
that the memory always-on flag can safely be cleared: the required memory
power-down/wake sequencing still needs investigation. Ordinary boot and
suspend continue to use the established policy.

## Persistent console for further diagnosis

The kernel previously lacked the ramoops backend, despite the stock DT
reserving 4 MiB for it. The persistent-root build now enables ramoops console
logging. The old framebuffer console used that same reservation for its own
progress log and refused to initialize with ramoops enabled; the initial test
therefore had no display KMS device and Hyprland aborted during startup.

The ownership fix keeps framebuffer setup and DRM takeover, while disabling
the custom C and MMU-off assembly log writes when ramoops is enabled. No
reserved-memory address or stock buffer split is changed. The boot helper
copies previous records to private 0700 directories with 0600 files. A benign
kernel log marker survived two clean RAM-boot transitions and was archived
correctly. This tests console retention, not a deliberately induced crash.

The MIF reset had also left the modem's deliberate startup-failure guard in
place. Bundle verification alone did not detect that automatic radio startup
was skipped. With CP offline and every modem service absent, the exact stale
guard was archived; the next boot reached the supervisor's `running` state
and exposed the telephony socket. Future recovery checks must include actual
registration and supervision, not just private-asset checksums.

The final logging image passed a normal RTC sleep/resume in the same boot:
one successful suspend, zero failures, intact synced 16 MiB storage checksum,
and live telephony prerequisites passing afterward. Wi-Fi SSH remained
available; host USB networking needed refreshing, and the original SSH stream
did not survive that cycle. This is not proof of seamless USB reconnection.

Installed image SHA256:
`5147bc4e1d401fa6adcd0eb1c973c417f841f58d7d3c7069fdb88605b74f2992`.
The installer verified the exact running kernel, desktop, old image hash and
partition layout before writing boot A, then verified direct readback. The
experimental MIF write API is absent. SICD permission/budget, Wi-Fi host link
sleep and UFS Hibern8 remain off by default. No camera capture was attempted.

Normal boot from the installed image passed: desktop, Wi-Fi SSH, 5,002 mAh
capacity, live modem registration/supervision, and recovery of the final
kernel's benign log marker. The guarded boot-metadata check found slot A
already marked successful; no boot-metadata write was needed.

## Standby baseline and the Wi-Fi hang

The first unplugged standby baseline (screen off, LTE and Wi-Fi up, the
normal s2idle policy) measured **348 mA** from the fuel gauge over 142
minutes (824 mAh, 97 % to 81 %), because the phone slept for only 0.4 of
those minutes. The first sleep worked; on its resume the BCM4389 firmware
stopped answering (its control ring filled: "Failed to reserve space in
commonring", query timeouts), Wi-Fi dropped, and the Wi-Fi endpoint
(0000:01:00.0) then refused every later suspend with -EIO, 244 times.

Repeated 15-second s2idle cycles hung the firmware in 2 of about 20 sleeps,
with either set of CPU-idle and MCT modules, so it is the intermittent
resume fault seen on September 29, not a new regression. Until its cause is
found, `pixel-suspend` recovers: when a suspend is refused by the Wi-Fi
endpoint and the firmware does not answer a query (`iw ... get power_save`),
it restarts the Wi-Fi stack (`scripts/pixel-wifi-restart.sh`, the boot
script's sequence) and the next attempt proceeds. The baseline has to be
measured again with that in place.

The second baseline was void for the same reason: the check never fired.
`iw ... get power_save` is answered from cfg80211's cache, so a hung chip
looked healthy (0.4 h: 16.6 of 34.9 minutes asleep, 470 mA). The check now
asks `iw ... info`, whose txpower line needs the firmware to answer
brcmfmac's qtxpower query (absent on the hung chip, present after a
restart), and treats a D3-entry timeout in the recent kernel log as a hang.

## The modem's screen state

While the modem service reports the screen on, the CP sends SIT indication
0x0906 about every 1.25 s (1,750 of about 1,800 indications in one boot);
each asserts CP2AP_WAKEUP and powers the PCIe link up. cpif then refuses every
deep suspend at `suspend_noirq` (CP2AP_WAKEUP high), and the link cycles
while the phone is awake. The stock screen-off messages the modem service
already implements (SIT 0902 screen state and the 0928 indication filter)
stop it: 16 indications in 20 s with the screen on, none with it off.
pixel-suspend sent them around each sleep but turned reports back on after
every wake, even while the display stayed dark. The shell now calls an
optional device display hook when the screen lights or goes dark
(`overlay/mobile/display-power.sh`); the Pixel's hook
(`scripts/pixel-display-hook.py`) sets the modem's screen state, and
pixel-suspend restores the state it found instead of forcing it on.

## SYS_SLEEP stage 5

The stage 4 register dump explained the modem crash: the bootloader leaves
the power-down state (CON_PDN/PUD_PDN) of the CP's control lines on gph1
(PDA_ACTIVE, CP_PWR_ON, CP_NRESET_N, CP_WRST_N) and of UFS RST_N and REFCLK
on gph3 at input with pull-down, so SYS_SLEEP pulled CP reset low. Stock
keeps them at their previous state. pixel-sleep now writes the stock
power-down states of the HSI1/HSI2 pins at arm, saves and restores the GPIO
banks of the powered-down domains, and compares (and restores) every
powered domain's stock save list. pixel-ufs gained a link-off deep-suspend
path (kernel/storage/README.md).

- The dry run (`pm_test=core`) armed cleanly: 8 pin states to change, 33 GPIO
  banks and 8 domain lists saved, nothing changed on the early path.
- Three UFS link-off round trips (deep, `pm_test=devices`, no firmware
  entry) re-initialized the host each time at HS-G4 with the probe file and
  a fresh write intact.
- The real SYS_SLEEP (RAM-booted image) entered and exited (`sleep_soc_down`
  and `sleep_mif_down` 0 to 1, woken by CP2AP_WAKEUP). HSI2 was power-cycled
  (IOCC read 0x10, SYSREG_HSI2's DRCG 0); 52 GPIO registers and 1 of 47
  CMU_HSI2 registers had lost their values and were restored. UFS link
  startup then failed five times, so root was lost and the runner rebooted.
  The modem crashed again (PHONE_ACTIVE low) after the 2.2 s the failing UFS
  resume held device resume, with the pin fix in place; the CP had asked
  for its link before the wake.

## Storage, Wi-Fi and the modem through SYS_SLEEP

Register diagnostics in pixel-ufs showed HSI2 losing everything in SYS_SLEEP:
the UFS host, UniPro and PHY registers, and SYSREG_HSI2, came back at their
reset values (CMU_HSI2 kept its state). The calibration then wrote every
sampled register back to its boot value, yet link startup failed. To iterate
without unplugging, pixel-sleep gained a test mode (`hsi2_cycle=2`, under
`pm_test=core`): stock's own HSI2 off/on sequence at arm, which reproduced
the same post-wake register state line for line. It needed four fixes:

1. **S2MPU.** Both S2MPU_HSI1 and S2MPU_HSI2 come back from a power cycle
   enabled (CTRL0 1), which stops all DMA of the domain; the bootloader
   leaves them disabled (0) and stock's pKVM restores them. pixel-sleep now
   saves CTRL0 at arm and writes it back first thing in the resume.
2. **The UFS DMA filter (SMU).** After the power cycle, commands without
   data passed and every READ timed out. The monitor's `SMU(INIT)` (SIP SMC
   0x1850) sets the filter up again; `FMP_SMU_RESUME` returns 0 but does
   nothing, as the bootloader, not the kernel, initialized it. The FMP
   descriptor-type call is not made: it selects 128-byte PRDT entries.
3. **UFS VCC.** Stock's level 5 switches the device's VCC (gpp0-1) off with
   the link. pixel-ufs now does the same and powers it up 10 ms before the
   reset, so the device is never left powered while VCCQ (a PMIC rail under
   pin control) drops in sleep.
4. **The pin power-down states**, above.

The monitor refuses DTZPC save/restore for HSI2 (stock never powers it at
runtime), which is why Wi-Fi did not come back in the emulation; in real
SYS_SLEEP the monitor handles it.

Stage 6 and 7 (unattended, USB connected): real SYS_SLEEP (`sleep_soc_down`
and `sleep_mif_down` 0 to 1, woken after 17 s by the modem's CP2AP_WAKEUP),
HSI2 power-cycled, both S2MPUs restored, UFS back at HS-G4 with the probe file
intact, root read-write, the USB gadget configured, Wi-Fi reloaded and
connected, and the modem still running and IMS-registered.

## Standby current through SYS_SLEEP (October 1, early morning)

pixel-battery gained two measurement aids: `input_off=1` puts the charger in
mode 0, so with USB still connected the phone runs from the battery and the
gauge counts its drain; `coulomb` reads the gauge's QH:QL counter in nAh
(charge_now moves in 2 mAh steps). Every USI (I2C and SPI engine) also loses
its configuration in SYS_SLEEP; after the first deep sleep the gauge's I2C
timed out. pixel-sleep now saves and restores the USIs the drivers use
(`pixel-sleep-usi.h`), after the CMU restore.

Measured from the battery, USB connected, display off, Wi-Fi unloaded:

| Configuration | Average |
|---|---|
| s2idle (today's policy), modem filtered | 286 mA |
| s2idle, modem stopped | 274 mA |
| SYS_SLEEP cycles, modem filtered (CP wakes every 8-20 s) | ~120 mA |
| SYS_SLEEP, modem stopped, 2-minute sleeps, stock PWREN rails | **79 mA** |
| ... and sensors stopped, Bluetooth drivers unloaded | 79 mA |

Sixteen-cycle runs came back every time with UFS, Wi-Fi, USB, the modem
(IMS registered) and the gauge working.

The stock DT lets PWREN switch 34 rails off in SYS_SLEEP; the bootloader
leaves them always on. `pixel-pmic-opmode suspend=` was bisected (a rail that
breaks the wake ends in a watchdog reset, which recovers the phone). Off in
sleep and passing: the CPU cluster bucks and LDOs, both GPU rails, both
PCIe PHY pairs, DP-AUX, L4M_HSI, MIF, VDDQ_MEM and the TCXO and PLL LDOs.
Not yet: S1S_VDD_CAM, L2S_PLL_MIPI_UFS and the two INT bucks, which stop the
wake. Stock powers DPU and DISP off through genpd before SYS_SLEEP; here they
stay on (the display is only blanked), which is the likely reason, and the
next thing to change. USB's share needs a measurement with the cable out.

A test mode (`pixel-sleep disp_off=1`) then powered DPU and DISP off at arm
with stock's genpd sequence (DTZPC save/restore accepted for both) and back on
at resume. With the display domains off, the whole stock PWREN set works,
INT, camera and the MIPI/UFS PLL included (`pixel-pmic-opmode suspend=all`):

| Configuration (modem stopped, USB connected) | Average |
|---|---|
| Display domains on, PWREN set without INT/CAM/PLL | 79.0 mA |
| Display domains off, same rails | 78.1 mA |
| Display domains off, all stock PWREN rails | **71.9 mA** |

So the display domains are what blocks those rails, but they are worth only
about 6 mA. The remaining ~72 mA is outside the SoC rails tested: the USB
connection itself (controller and PHY active, the host polling), and the
external parts nothing puts in a low-power state (panel left in sleep mode,
touch controller, Wi-Fi/BT, GNSS). Next: the same run unplugged.


## Where the SYS_SLEEP floor goes (October 1, morning)

The averages above include the wakes. `elim.sh` (session scratch; same setup as
the 68 mA run: all stock PWREN rails, display domains off, modem stopped,
Wi-Fi unloaded, USB connected with the charger input off) reads the gauge's
coulomb counter right around each `rtcwake` and sleeps twice per
configuration, 30 s and 150 s. The slope between the two is the current
while asleep, the intercept the cost of one sleep/wake round trip.

- **A wake costs 0.01–0.05 mAh.** The 68–78 mA is drawn while the SoC is in
  SYS_SLEEP, not by wake-ups.
- Cumulative steps, round 1:

  | Step | Asleep |
  | --- | --- |
  | baseline | 77.4 mA |
  | touch IC held in reset (`pixel_touch_input` unloaded) | 72.8 mA |
  | sensor proxy stopped | 73.1 mA |
  | Bluetooth drivers unloaded (BT_REG_ON low) | 72.7 mA |

- Round 2, from a cold start of the test image: baseline with touch in reset
  64.4 mA; amplifiers unloaded (AoC sound card first, then the CS35L41
  driver, which drives their reset low) 63.4 mA.
- Round 1's 13 mA higher baseline followed a warm reboot from a camera
  session in which `pixel-camera-power` was never unloaded. The S2MPG13 keeps
  the SLG51002 enable lines across a warm reboot, so the camera PMIC most
  likely stayed up. Unload the module (or power the SLG51002 down) before
  rebooting after camera work.
- Wi-Fi: unloading brcmfmac and pixel-pcie already leaves WL_REG_ON and PERST#
  low (gph2 DAT 0x2), so the BCM4389's Wi-Fi side is off in these runs.
- So far only touch (≈5 mA) and the amplifiers (≈1 mA) have measured.

ODPM's `interval_power` cannot split the rest yet: the accumulators read back
frozen (sample count pinned at 0xfffff, identical values across intervals),
and neither ASYNC_RD nor turning the meters off and on clears them.
- Round 3 booted without the AoC (the audio start marker set, so neither the
  AoC firmware nor its microphone and sensor rails came up): 63.0 and 62.7 mA
  with touch in reset. The AoC, its rails and the amplifiers together are
  worth about 1–1.5 mA in SYS_SLEEP.
- Round 5 read ODPM around two 150 s sleeps, after the meter reset fix
  (kernel/odpm). The meters keep sampling through SYS_SLEEP (18,770 samples
  in 151 s).
  - The external shunts read near zero: display 0.0 mW, modem 0.2 mW,
    Wi-Fi/BT 0.3 mW, RF front end and mmWave 0.
  - The internal rails are not credible in sleep. They add up to 750 mW
    while the battery supplies about 250 mW (65 mA), and the CPU cluster
    rails show their awake values although PWREN switches them off. They
    look like the last sample repeated.
  - So the floor is not in the VSYS loads. It is in the SoC, memory or PMIC
    side, or in loads no meter covers.

### Touch held in reset at screen-off (October 1)

The touch controller was the one part worth a measurable share (≈5 mA in
SYS_SLEEP). `pixel_touch_input` now has a writable `sleep` parameter: 1
releases all contacts and holds the S3908 in reset, as the bootloader leaves
it; 0 restarts it with the usual reset timing and identify check (about
0.25 s, most of it the controller's 200 ms boot).
`pixel-display-hook` writes it on every screen change, so the controller is
off whenever the screen is dark, awake or asleep. The boot script loads a root
copy (`/usr/local/lib/omarchy-mobile/pixel_touch_input.ko`) when present.

Still unmeasured: USB's share. Every SYS_SLEEP figure above was taken with the
cable in (gadget configured, HSI0 and the USB PHY rails on); the "about 4 mA
less unplugged" noted on October 1 was an estimate, not a measurement. The
next floor measurement needs the cable out.

### USB's share: a software disconnect hung the phone (October 1, night)

To measure USB's share without pulling the cable, `elim6.sh` (session
scratch) ran the usual setup in the RAM-boot test image, measured a 30 s and
a 150 s SYS_SLEEP with the gadget connected, then again after
`soft_connect` = disconnect on the dwc3 UDC, then after unbinding dwc3, and

## Daily SYS_SLEEP, first unplugged measurement (October 1)

With boot image deepsleep-image-2 in boot_a, `pixel-suspend` uses SYS_SLEEP
for every screen-off sleep (see `scripts/pixel-suspend.py`). The first
unplugged run (screen off, modem registered, Wi-Fi unloaded while dark, one
15-minute background check) averaged **99.7 mA over 1,219 s** (33.8 mAh),
about a third of the old s2idle standby (286–334 mA). The modem woke the phone
27 times in 11 minutes, about every 25 s. The adapter put it straight back to
sleep each time, but each quiet wake still kept it up about 4.6 s. The
background check stayed up about 50 s (Wi-Fi reload plus the shell's 45 s
hold).

The 4.6 s broke down as: 0.3 s for suspend and resume, 2 s of BlueZ resume,
2 s of fixed settle in the adapter, and 0.3 s of requests to the modem
service. A stack sampler on the adapter
(`/root/tools/stack-sample.py`, session scratch) showed the 2 s inside
`pm_suspend`, after the tasks thaw: `hci_suspend_notifier` → `hci_resume_dev`
→ `hci_set_event_mask_sync` waiting out the 2 s HCI command timeout.

**Bluetooth did not survive SYS_SLEEP.** BT_REG_ON (gpp16-2) is a PERIC0 pin.
In SYS_SLEEP its pads take their power-down settings, and CON_PDN 0xaa makes
it an input, so the chip loses power. After the wake the pin drives high
again, but the chip is back in its ROM: no patch firmware, 115200 baud. Every
command at 3 Mbaud timed out, so Bluetooth stayed dead until reboot.
Unloading and reloading hci_uart and pixel-bt brings it back.

Fixes (installed on the phone, not in the boot image):
- `pixel-suspend` unloads hci_uart and pixel-bt before deep sleep, which
  drives BT_REG_ON low, and leaves `/run/pixel-bt-sleeping`. When the screen
  lights, `pixel-display-hook` runs `pixel-bt-restart`
  (`scripts/pixel-bt-restart.sh`). bluetoothd powers hci0 again on its own.
- The fixed 2 s settle after a modem wake is gone. The adapter now:
  1. waits for the wake locks to clear (the `wakeup_count` read). The modem
     holds `s5100_wake_lock` and its channel wake locks while it sends.
  2. allows 0.3 s for the service's 50 ms read loop.
  3. checks the service's text and call indication counts, the message
     store, and live calls.

  One plugged-in quiet wake went back to sleep 1.4 s after resume: about
  1.0 s waiting on the modem's wake locks, then the settle and requests.
  Including suspend and resume, that is about 1.7 s awake per quiet wake,
  down from 4.6 s.
- The shell (`overlay/mobile/sleep.py`) ends the background check's hold 15 s
  after NetworkManager reports `connected`. The 45 s hold remains the cap.
- `pixel-wifi-restart --start` only loads Wi-Fi that is not loaded, and runs
  hold a lock. The adapter and the display hook both start Wi-Fi after a
  power-key wake and could race.
- Each deep-sleep result now has `deep_ma`: the gauge's coulomb counter
  around every state write, divided by the time slept. It includes each
  sleep's entry and exit.

### Second unplugged run, with the shorter wakes (October 1, afternoon)

The same conditions for 2,413 s, with three background checks' worth of
sleep. It averaged **63.6 mA** (42.6 mAh), down from 99.7 mA.
- The phone was in deep sleep 95.3% of the time. The adapter's `deep_ma`
  read 50.4, 49.7 and 49.9 mA for its three calls. That puts the floor at
  about **50 mA** unplugged with the modem registered, entry and exit
  included, so about 32 of the 42.6 mAh. The cable-in floor measured with the
  modem stopped was 63 mA, so USB costs more than the modem does here.
- The 114 s awake used about 10.7 mAh (~340 mA average). That time was:
  - the first minute and a half after unplugging;
  - two background checks, each about 34–38 s between sleeps (Wi-Fi reload,
    connect, then the 15 s hold, plus the adapter's own overhead);
  - 13 quiet modem wakes.
- The modem woke the phone far less than in the first run: 13 quiet wakes in
  40 minutes, against 27 in 11 minutes. Wake-source deltas:
  `s5100_wake_lock` 12 wakeups, `pixel-rtc` 4, `pixel-keys` 2. Its RFS
  channel (`umts_rfs0`) saw 702 events; modem indications were 0906 ×6 and
  0604, 074b, 0d05 once each. Nothing in this run shows why the rate
  changed between runs.
- Afterwards Bluetooth, Wi-Fi and the modem were all back, and nothing was
  logged. Each Bluetooth reload re-applies pixel-bt's overlay, and its
  removal leaks the `__symbols__/pixel_bt_clk` property (the kernel's "memory
  leak will occur if overlay removed" warning). That is a few hundred bytes
  per screen-on after a deep sleep.

The floor is now three quarters of the energy. The remaining 50 mA → 25 mA
is the next work: the display domains and the INT, CAM and PLL rails left on
in sleep. ODPM can't split it yet: its meters keep sampling through SYS_SLEEP,
but the internal rails don't read credibly there (round 5 above), and the
external shunts read near zero.
