# September 30: capacity correction and deeper-idle bring-up

The installed battery-model image reports 5,002 mAh from the matched stock
Lishen profile, replacing the uninitialized 3,000 mAh gauge default. The
installed image retains the tested modem, USB switch recovery and key-only
Wi-Fi SSH. This capacity correction is not a standby-power measurement.

The later system-idle work remains opt-in. It is not enabled by the persistent
boot helper. The installed diagnostic image includes these default-disabled
options, the battery correction and persistent console logging; ordinary boot
uses the established sleep policy. The prior battery-model image is retained
as a recovery artifact.

## Validated prerequisites

- UFS Hibern8 system suspend enters and resumes with zero CDR timeouts; a
  synced 16 MiB test file remains intact. The feature defaults off.
- Read-only CPU/PCIe/ACPM checks showed the modem host powers down but the
  Wi-Fi host previously retained L1. Normally unloading Wi-Fi exposed idle
  opportunities with drained firmware queues.
- The CPU module now wraps both regular and frozen-tick idle callbacks.
  Frozen-tick idle uses an unbounded local timer deadline. Measurements use
  the architectural counter because monotonic time freezes during s2idle.
- A bounded, optional CPU 0 retry makes a little CPU enter last. Without it,
  CPU 7 entered last in a recorded trial, leaving no eligible little CPU to
  request the system mode. All physical-core and device guards remain.
- Optional Wi-Fi host PM reaches L2, powers down and isolates its PHY, then
  retrains and restores L1 substates before the network stack resumes. It
  preserves endpoint firmware power. The shared IRQ is synchronized before
  isolation, and isolation is released before any resume register access.

## Hardware evidence

A coordinated SICD hint covered 9.147 seconds of a 9.148-second RTC sleep,
with no cancellation or errors. Two later intervals covered 9.308 and 9.325
seconds. These alone did not establish a power saving: partial-rail totals
were 861.4/866.2 mW against controls of 863.1/863.2 mW.

A read-only ACPM named-buffer diagnostic then confirmed that an 8.369-second
combined Wi-Fi/UFS/SICD trial advanced the firmware's SoC-down and SICD
SoC-down counters from 0 to 1, with no early wakeup. The memory-interface
counter stayed 0 and its `mif_always_on` flag stayed 1. This is the remaining
firmware-policy lead; no policy flag was changed for that measurement.

Wi-Fi host PM passed an 8.604-second RTC cycle, and an 8.888-second combined
UFS/SICD cycle. Wi-Fi HTTPS and modem verification passed afterward. All
trials resumed in the same boot. The wake-enabled endpoint was first refused
cleanly; tests then temporarily disabled Wi-Fi wake and restored it afterward.
These tests do not establish wake-on-Wi-Fi, camera support, speakerphone, or
unplugged battery life.

## Defaults and recovery

`permit_sicd` and `sicd_defer` default false; `sicd_budget` defaults zero.
`system_link_off`, UFS `system_hibern8`, and watchdog `keep_running` also
default false. The extra system-mode mappings are only created when permitted.
The watchdog diagnostic reloads an already armed watchdog during short sleep;
it must be disabled for normal long sleeps. Reset recovery depends on its
clock continuing to run.

All trial scripts restore these runtime flags. No modem identity, SIM data,
firmware binary or private diagnostic output is tracked. The phone-side
modem manager owns radio control and the existing watchdog feeder throughout.
See the [CPU idle](../kernel/cpupm/README.md),
[Wi-Fi host](../kernel/pcie/README.md), and
[firmware diagnostics](../kernel/suspend/README.md) notes for implementation.

## Memory-sleep trial: not suitable for use

A subsequent RAM-only experiment followed the stock FLEXPMU debug control:
clear `MIF_ALWAYS_ON` only after all SICD guards pass, save its original value,
and restore it on wake or cancellation. The trial was limited to one entry
with a ten-second RTC alarm and an already armed watchdog left running.

The phone did not return through the trial cleanup. It reset and reconnected
roughly a minute later in the installed battery-model image. This timing is
consistent with the watchdog fallback, but no boot-reason field or persistent
crash record was available to confirm the reset cause or exact failure stage.
The pre-trial record was synced; no post-sleep counters were saved. Modem
verification, Wi-Fi access, the synced storage checksum and 5,002 mAh capacity
reporting all passed after recovery.

The MIF write API and its CPU-module option were removed from build sources.
The experimental patch and result remain private research artifacts. Only the
tested read-only firmware-counter implementation is retained. Do not infer
that the memory always-on flag can safely be cleared: the required memory
power-down/wake sequencing still needs investigation. Ordinary boot and
suspend continue to use the established policy.

## Persistent console for further diagnosis

The kernel previously lacked the ramoops backend, despite the stock DT
reserving 4 MiB for it. The persistent-root build now enables ramoops console
logging. The old framebuffer console used that same reservation for its own
progress log and refused to initialize with ramoops enabled; the initial test
therefore had no display KMS device and Hyprland aborted during startup.

The ownership fix keeps framebuffer setup and DRM takeover, while disabling
the custom C and MMU-off assembly log writes when ramoops is enabled. No
reserved-memory address or stock buffer split is changed. The boot helper
copies previous records to private 0700 directories with 0600 files. A benign
kernel log marker survived two clean RAM-boot transitions and was archived
correctly. This tests console retention, not a deliberately induced crash.

The MIF reset had also left the modem's deliberate startup-failure guard in
place. Bundle verification alone did not detect that automatic radio startup
was skipped. With CP offline and every modem service absent, the exact stale
guard was archived; the next boot reached the supervisor's `running` state
and exposed the telephony socket. Future recovery checks must include actual
registration and supervision, not just private-asset checksums.

The final logging image passed a normal RTC sleep/resume in the same boot:
one successful suspend, zero failures, intact synced 16 MiB storage checksum,
and live telephony prerequisites passing afterward. Wi-Fi SSH remained
available; host USB networking needed refreshing, and the original SSH stream
did not survive that cycle. This is not proof of seamless USB reconnection.
